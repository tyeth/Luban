# A350 USB serial probing trial

Status: reviewed plan with a limited live USB trial. The four-face probe and probe tool setter completed over Wi-Fi. A350 USB text serial connected, was homed, and completed non-contact XY moves. The 25 mm contact trial remains blocked on motion-completion, query, and stop qualification. This document authorizes no further motion or firmware reset. See [linked issues](usb-serial-linked-issues.md).

## Goal and baseline

Determine whether Luban's USB serial channel can provide reliable command completion and fresh position feedback for MCP sensor-gated probing, and whether it reduces end-to-end step latency without reducing contact safety. Keep the GPIO probe, tool setter, and overtravel feed on the current KB2040/U2IF bridge; only the machine G-code link changes.

Preserve the four-face job result and its `result.timing`, per-step `execMs`, `senseMs`, position rechecks, and any slow-step events. Compare USB timing against actual Wi-Fi job timing, not a nominal feed calculation.

Completed Wi-Fi baseline (2026-11-01): four-face procedure `cec56d992ef8` finished 7/7 operations in 811.2 s with 649 command batches. One contact at machine X170 Y200 per index: B0 toolhead Z207.0, B90 Z219.2, B180 Z201.0, B270 Z219.6 mm; each had three identical confirmation contacts. The result contains 621.9 s of command API time, including 355.1 s calculated nominal motion, plus 181.2 s sensor windows (which overlap idle time). The setter procedure `6e0267c3e33a` then measured trigger machine Z171.5 mm on three passes with zero spread and a 71.0 mm conventional probe projection from its configured setter datum. That datum is a legacy reference convention, not independently verified physical clearance. The setter ended at verified machine X79 Y293 Z328, B270, homed and idle; GPIO probe, setter and overtravel channels were connected and untriggered. Verify fitted tool identity, calibration applicability and the live pose again immediately before any later connection change.

## Phase 1: serial connection, no motion

1. With all jobs finished and the machine idle, record `get_connection_status`, `get_position`, `get_probe_feed_status`, and `get_mcp_diagnostics`. Note the active workspace and origin offset. Record the verified final pose; if not already at machine toolhead Z328, a raise requires its own authorized staged move before switching.
2. Only after phase 0 passes, in Luban's normal Connection UI, disconnect Wi-Fi and select the A350's identified USB serial port. Do not open the serial device from another process or send commands outside Luban. Verify the machine port is distinct from the KB2040/U2IF bridge. Record stable device identity, new connection generation, selected port, baud rate, detected protocol (plain-text Marlin or SACP over serial), firmware/machine identity, and `get_connection_status` channel name/type.
3. Require Luban to report connected and ready, a fresh reliable machine position (`verified`, `heartbeat`, or `cached-offset`), empty position warnings, homed and idle, and a coherent B angle and origin offset. If position is `awaiting-resync`, stale, implausible, or in an unknown frame, stop here and diagnose through `query_firmware_position` and MCP diagnostics. A serial connection alone does not prove motion readiness. Re-establish connection-scoped frame/offset trust; pre-switch setter records remain measurement evidence but cannot be treated as a same-connection tool-change pair. HTTP recover_machine_connection is not a serial recovery mechanism.
4. Run only the exact channel's supported small read-only query set through MCP: `query_firmware_position` (M114) repeatedly, then `query_firmware_configuration` (M503 S) once if supported. Capture raw replies, elapsed time, heartbeat/report age, and whether each returned position agrees with the position of record. For text serial, require attributable reply text; queued-only `ok` blocks the trial. For installed SACP, a documented null raw reply is expected: require the separately qualified coordinate subscription and completion contract instead. An ACK is not position proof. Unsupported M503 is a capability result, not a reason to reconnect or reboot. M114 reports the selected frame and does not independently prove the workspace or an old offset. Use the existing MCP/Connection UI for any supported mode switch; do not send a reboot or mode-switch G-code speculatively.
5. Check the GPIO feed independently after USB connection: all three channels enabled, fresh, untriggered, no latched alarm. An optional manual probe-switch press while idle can timestamp trigger/release reporting. It does not test crash stopping: idle tripwires are unarmed.

## Phase 2: minimum motion trial

Only after phase 1 passes, take a fresh preflight (connection, reliable position, homed/idle, stored landmarks and limits, fitted probe, GPIO feeds). The requested trial is now a **25 mm maximum −Z search, in 1 mm checked increments, with a stable object in the approved path**. Secure the object before staging; record its placement, machine XY column, start toolhead Z, search floor, B, probe-body clearance and retreat. Do not use a hand-held object or move it during the procedure. An object in the path does not itself establish a clear transit or approach.

Stage one `probe_sequence` with `coarse_step_mm: 1`, normal finer confirmation and one `dz: -1` probe with `max_travel_mm: 25` and explicit `on_miss: "abort"`. Stop on contact; this is an up-to-25-mm search, not a demand to move the whole distance. The runner also releases, fine-probes, confirms and retreats, so cumulative travel exceeds the search span. The confirm page must show that full behavior, frame, floor and recovery. Successful completion returns to machine toolhead Z328; held contact must remain held.

Start from a proven-safe pose within the 25 mm search envelope. Do not descend blindly based on an estimated object height. The old X170/Y200 face contact can support an approach only for its unchanged column, stock, B and fitted tool; it does not qualify a newly placed object. If reusing that measured face, a start about 24 mm above its contact (within travel) keeps the maximum floor about 1 mm below contact. **Do not retain the old 4 mm-above approach while increasing the bound to 25 mm:** it would allow 21 mm beyond the previous contact after a missed trigger. Contact is toolhead machine Z, not physical surface height. State stylus/body clearance and the permitted no-contact floor explicitly.

`max_travel_mm` bounds the probe march, not the preceding approach. Source `probeSequence.ts:377–386` uses approach segments up to 5 mm before its final guarded descent. If the 1 mm requirement applies throughout the approach, start the march at the proven safe pose or qualify a runner that checks every approaching segment at ≤1 mm. Do not describe the existing `descend` step as wholly 1 mm. Deliver the staged confirm link and end the turn before waiting for approval.

Capture each increment's dispatch, queue/write, ACK, independently established physical completion, M114/heartbeat position, sensor reading and release, `execMs`, `senseMs`, and stop/retreat outcome. Current `execMs` measures API-return latency; it is not automatically controller or motion time. A 10 ms GPIO polling interval is not end-to-end latency; source `senseAfter` checks in up-to-50-ms waits (`probing.ts:591–634`). Never queue the next approach increment until physical completion and the sensor verdict. The contact must occur within the planned bound, and final position must be reverified. If the command API only reports queue acceptance, if the sensor triggers unexpectedly, if the frame flips, or if feedback becomes stale, stop the test under the existing crash/hold rules.

## Phase 3: compare qualified transport performance

Resolve phase 0 blockers before any contact trial. Do not discover completion, stop or frame contract failures by reducing live timeouts.

If the contracts hold, compare at least several equivalent increments or contacts on the same proven column across transports. Keep the same tool, B, column, feeds, sensor windows and confirmation count; changing the object or approach makes whole-job timings non-comparable. Report sample counts, median and observed maximum latencies (a single short trial cannot establish a reliable tail percentile) for command completion, position feedback, GPIO feed, whole sensor-gated step, and full up-to-25-mm trial. Keep the initial proven 300 ms sense windows; reduce waits only after safety contracts pass and measured data supports it (GPIO is currently polled at 10 ms, while the present job's sense windows are 300 ms); retain contact debounce, release verification, bounded 1 mm travel, and abort/held-contact behavior. Do not tune by simply raising feed or coarse-step size.

## Failure and recovery checks

Exercise fault injection in mocks before live connection; any physical stop demonstration needs a separate reviewed safe procedure. Cover: no serial reply, wrong protocol detection, stale or contradictory M114, missing origin offset, disconnected USB, and unavailable GPIO bridge. For code tests, simulate delayed/partial/out-of-order serial replies, a command queued but never completed, a connection loss mid-march, a probe already triggered, and an unexpected tripwire trigger. Also simulate ACK before planner completion, target reported while still moving, G53-window offsets, concurrent UI queries, a failed line with a queued batch tail, fresh status with stale coordinates, callbacks from an old connection, transient touch/release, GPIO failure mid-step, and missing/failed stop methods. Each must block further approach commands, prevent old-session continuation, preserve partial evidence and report its actual held/unknown state. A procedure stop is not an emergency stop. A firmware reboot or mode-switch G-code is a later, separately reviewed action only if read-only evidence shows it is necessary; record the pre-reset state and expected re-homing/work-origin consequences first.

## Exit criteria

Report three separate outcomes: connectivity/position qualification, safe completion of the up-to-25-mm contact/recovery trial, and measured timing improvement or regression. Require attributable M114 or the explicitly qualified SACP alternative plus physical completion evidence. A safe but slower USB result is valid evidence; it is not a reason to weaken safety gates. Otherwise retain the proven Wi-Fi path and turn the observed gap into a focused MCP/Luban change with tests.
